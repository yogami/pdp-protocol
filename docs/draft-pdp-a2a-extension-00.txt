       Proof of Execution Extension for A2A Agent Discovery (PoE-A2A)
                          draft-pdp-a2a-extension-00

Abstract

   This document specifies a lightweight extension to the Google A2A
   Agent Discovery protocol that adds verifiable Proof of Execution
   (PoE) claims to AgentCards. Agents advertise cryptographically
   signed execution proofs via standard HTTP endpoints, enabling
   trust-first discovery without gossip protocols or mandatory 
   blockchain transactions.

   This extension is designed for on-demand verification of historical
   agent performance and compliance.

1.  Introduction

   The Agent-to-Agent (A2A) protocol provides HTTP-based discovery via
   AgentCards served at /.well-known/agent-card.json. However, current
   AgentCards rely on self-reported capabilities without verification.

   This extension adds a "poe_claims" field to AgentCards, containing
   signed attestations of completed work. This document defines the
   schemas and endpoints for discovering and verifying these claims.

   Author: Berlin AI Labs (contact@berlinailabs.de)

2.  Terminology

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",
   "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this
   document are to be interpreted as described in RFC 2119.

   PoE Claim: A signed attestation of completed work.
   
   Proof Bundle: The full execution artifacts (fetched on-demand).
   
   Anchor: An optional on-chain record of the PoE hash.

3.  Design Philosophy

   3.1.  HTTP-First

   A2A already uses HTTP. This extension adds PoE without requiring
   agents to join P2P networks or pay blockchain fees for discovery.

   3.2.  Fetch-on-Demand

   AgentCards contain only claim metadata. Full proofs are fetched
   from a separate endpoint when verification is needed.

   3.3.  Optional Anchoring

   Blockchain anchoring provides additional assurance but is NOT
   required for basic discovery.

   3.4.  Incremental Adoption

   Existing A2A agents can add poe_claims without breaking changes.

4.  AgentCard PoE Extension

   Agents SHOULD include a "poe_extension" field in their AgentCard:

   {
     "name": "Example Agent",
     "description": "Task automation agent",
     "protocol_version": "A2A/1.0",
     "capabilities": ["code-review", "security-audit"],
     
     "poe_extension": {
       "version": "PoE-A2A/1.0",
       "signing_key": "ed25519:base64-pubkey",
       "claims_count": 47,
       "claims_endpoint": "/.well-known/poe-claims.json",
       "proof_endpoint": "/.well-known/poe-proofs/{claim_id}",
       "authorized_anchors": ["solana:address", "base:address"],
       "anchors": {
         "solana": "optional",
         "base": "optional"
       }
     }
   }

   4.1.  Field Definitions

   - signing_key: Ed25519 public key for claim verification (REQUIRED)
   - claims_count: Total verified claims (REQUIRED)
   - claims_endpoint: URL to fetch claim list (REQUIRED)
   - proof_endpoint: URL template to fetch full proofs (REQUIRED)
   - authorized_anchors: List of addresses authorized to anchor on 
     behalf of this agent (RECOMMENDED)

5.  PoE Claim Format

   Claims are served at the claims_endpoint as a JSON array:

   [
     {
       "id": "claim-001",
       "key_id": "v1",
       "task_hash": "sha256:hex",
       "output_hash": "sha256:hex",
       "timestamp": 1707000000000,
       "valid_until": 1738600000000,
       "capabilities_used": ["code-review"],
       "signature": "ed25519:base64-sig",
       "anchor": {
         "chain": "solana",
         "tx": "base58-sig"
       }
     }
   ]

   5.1.  Claim Fields

   - id: Unique claim identifier (REQUIRED)
   - key_id: ID of the key used for signing (REQUIRED)
   - task_hash: SHA-256 of task input (REQUIRED)
   - output_hash: SHA-256 of task output (REQUIRED)
   - timestamp: Unix milliseconds of execution (REQUIRED)
   - valid_until: Expiration of this claim (RECOMMENDED)
   - capabilities_used: Which capabilities were exercised (REQUIRED)
   - signature: Ed25519 over claim fields (Section 5.2) (REQUIRED)

   5.2.  Signature Computation

   The signature MUST be computed over a canonical JSON representation
   of the claim fields (Section 5) excluding the "signature" field.

   Implementations MUST use RFC 8785 (JSON Canonicalization Scheme).

   Example signing input (JCS):
   {"capabilities_used":["code-review"],"id":"claim-001","key_id":"v1",
    "output_hash":"sha256:...","task_hash":"sha256:...","timestamp":...}

   5.3. Key Rotation Format (poe-keys.json)

   Agents supporting key rotation MUST serve a JSON object at 
   /.well-known/poe-keys.json:

   {
     "keys": [
       {
         "key_id": "v1",
         "public_key": "ed25519:base64-pubkey",
         "valid_from": 1707000000000,
         "valid_until": 1738600000000,
         "revoked": false
       }
     ]
   }

6.  Verification Endpoints

   6.1.  Claim List

   GET /.well-known/poe-claims.json
   
   Implementations SHOULD support pagination via ?offset=N&limit=M

   6.2.  Full Proof

   GET /.well-known/poe-proofs/{claim_id}
   
   Returns a JSON object representing the Proof Bundle:

   {
     "claim_id": "claim-001",
     "task_input": "...",
     "task_output": "...",
     "execution_artifacts": {
        "logs": ["..."],
        "zk_proof": "optional-hex"
     },
     "integrity_hash": "sha256-of-entire-bundle"
   }

7.  Optional Blockchain Anchoring

   7.1.  Anchor Verification
   
   When an anchor tx is present, verifiers MUST check:
   - Transaction data contains the output_hash.
   - Transaction was signed by an address in "authorized_anchors".

   7.2.  Supported Chains
   
   Solana (Memo Program) and Base L2 are supported in this version.

8.  Security Considerations

   8.1.  Claim Freshness: Verifiers MUST reject claims where 
         valid_until < current_time.
   8.2.  Replay Protection: Verifiers MUST track seen claim IDs.
   8.3.  Endpoint Authentication: Implementations SHOULD require mTLS
         or API keys for full proof endpoints to prevent DoS.
   8.4.  Session Smuggling: PoE attests to outputs, not safety. 
         Orchestrators MUST perform real-time intent validation.

9.  IANA Considerations

   Requests registration of /.well-known/poe-claims.json and 
   /.well-known/poe-keys.json.

Appendix A.  Design Archetypes (Informational)

   A.1.  Sovereignty and Interoperability

   Agents using PoE-A2A maintain verifiable reputation across 
   providers, enabling "sovereignty by design." This is critical for 
   independent agents in decentralized ecosystems.

Appendix B.  Enterprise Compliance and Badges (Informational)

   B.1.  PoE-Verified Status: Agents with >100 anchored proofs MAY
         advertise a "PoE-Verified" status for corporate discovery.
   B.2.  Visual Badges: A dynamic SVG badge endpoint MAY be exposed
         at /.well-known/poe-badge.svg for visual discovery.
